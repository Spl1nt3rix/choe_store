# Универсальный гайд: как адаптировать проект к другому заданию такого же типа

## 1. Что взять за основу из проекта-примера

Полезные архитектурные идеи, которые обычно встречаются в аккуратно организованных проектах:

- **Разделять ответственность по файлам.** Настройки подключения — отдельно; запросы к БД — в репозитории; авторизация — отдельная функция/модуль; окна — в `screens/`.
- **Проверять роль пользователя в одном понятном месте.** Гость, клиент, менеджер и администратор должны видеть только предусмотренные заданием действия.
- **Не хранить пароль PostgreSQL прямо в коде репозитория.** Использовать переменную окружения или локальную настройку, не добавлять секреты в Git.
- **Переиспользовать формы и функции сохранения.** Добавление и редактирование часто могут использовать одну форму; SQL-запросы не стоит копировать в каждый экран.
- **Проверять ввод до сохранения.** Обязательные поля, числа, диапазоны скидки, даты, уникальные артикулы.
- **Показывать понятные сообщения об ошибках.** Например, если запись используется в заказе, объяснить, почему удаление невозможно.
- **Держать изображения отдельно от БД.** В таблице хранить относительный путь к файлу, если это соответствует заданию.

Не копируйте проект друга целиком без проверки: названия таблиц и полей, стек, права ролей и правила предметной области могут отличаться от вашего задания. В текущем проекте используется PostgreSQL и поля `user_id`, `login`, `password_hash`, `role_id`; чужие запросы с `users.id` или `users.username` не подойдут без адаптации.

## 2. Что установить

### Приложения

1. **Python 3** — интерпретатор Python. Для экзамена заранее проверьте версию, разрешённую организаторами.
2. **PostgreSQL** — сервер базы данных.
3. **pgAdmin 4** — графический интерфейс для создания базы, таблиц, связей, запуска SQL и резервного копирования.
4. **Visual Studio Code** или **PyCharm** — редактор кода. Подойдёт и другая разрешённая среда.
5. **Git** — необязателен для запуска, но полезен для сохранения версий проекта.

### Python-библиотеки проекта

Устанавливайте зависимости из `requirements.txt`, а не вручную по одной:

```bash
python -m venv venv
source venv/bin/activate       # Fedora/Linux
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Windows PowerShell:

```powershell
py -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

В текущем проекте нужны:

- `PyQt6` — графический интерфейс;
- `psycopg2-binary` — подключение Python к PostgreSQL;
- `bcrypt` — проверка хешей паролей;
- `PyInstaller` — необязательная сборка исполняемого файла.

Если в новом задании нужны Excel/CSV-импорт или экспорт, могут понадобиться `pandas` и/или `openpyxl`; добавляйте их только если этого требует задание или код.

## 3. Как подготовить проект под новое задание

### Шаг 1. Выписать требования

Из текста задания выделите отдельные списки:

- таблицы, поля, типы, первичные и внешние ключи;
- роли и разрешённые действия каждой роли;
- экраны и кнопки;
- поиск, сортировка, фильтры;
- правила проверки данных;
- обязательные файлы на сдачу: исходники, SQL-дамп, ERD, блок-схема, документация, исполняемый файл — только если он требуется.

Не добавляйте функции «для красоты», пока не выполнены обязательные требования.

### Шаг 2. Сопоставить схему БД

Составьте таблицу соответствий:

| Вопрос | Что проверить |
|---|---|
| Таблица существует? | Точное имя таблицы |
| Поле существует? | Имя и регистр/написание |
| Тип совпадает? | Например, `INTEGER`, `NUMERIC`, `DATE`, `VARCHAR` |
| Связь верна? | FK указывает на правильный PK |
| Есть ограничения? | `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT` |

После этого обновите SQL-запросы в `data/repository.py`. Если в новом задании поле называется `article`, нельзя незаметно заменить его на `id` или наоборот.

### Шаг 3. Настроить базу

- Для **пустой** базы используйте `init_db.sql` как исходную схему текущего проекта.
- Для **уже существующей** базы не запускайте `init_db.sql` повторно: он создаёт таблицы заново и предназначен для пустой БД.
- Изменения для существующей схемы оформляйте отдельным миграционным SQL-файлом и запускайте только после проверки его назначения.
- Проверьте связи через ERD Tool в pgAdmin.
- Сделайте резервную копию через Backup; для SQL-скрипта выбирайте формат Plain, если этого требует задание.

### Шаг 4. Подключить Python

В `db.py` проверьте имя базы, пользователя, хост, порт и пароль. Можно использовать переменные окружения `SHOESTORE_DB`, `SHOESTORE_USER`, `SHOESTORE_PASSWORD`, `SHOESTORE_HOST`, `SHOESTORE_PORT`. Не публикуйте пароль в Git и не отправляйте его в скриншотах.

Проверяйте подключение до запуска интерфейса. Если вход не работает, проверьте одновременно:

1. доступность службы PostgreSQL;
2. имя базы и пользователя;
3. пароль и переменные окружения;
4. названия полей в SQL-запросе;
5. формат хеша пароля в `password_hash`.

Хеши разных алгоритмов не взаимозаменяемы. Если приложение ожидает bcrypt, обычный SHA-256-хеш нельзя проверить функцией `bcrypt.checkpw`.

### Шаг 5. Реализовать логику и интерфейс

- Запросы к БД держите в `data/repository.py`.
- Экраны и диалоги держите в `screens/`.
- Используйте параметризованные SQL-запросы (`%s` или именованные параметры), а не склеивание пользовательского ввода в SQL.
- Для сортировки используйте только список разрешённых полей.
- Проверяйте права не только скрытием кнопки, но и перед выполнением операции.
- После сохранения обновляйте список; перед удалением показывайте подтверждение.
- Ошибки уникальности и внешних ключей объясняйте понятным сообщением.

### Шаг 6. Пройти тестовый сценарий

Минимально проверьте:

- неверный логин/пароль и корректный вход;
- каждую роль отдельно;
- видимость и доступность кнопок;
- пустые обязательные поля;
- границы числовых значений;
- поиск, сортировку и фильтр;
- создание, изменение и удаление записи;
- попытку удалить запись, на которую ссылается другая таблица;
- уникальные значения и ограничения дат;
- перезапуск приложения и сохранность данных.

### Шаг 7. Подготовить сдачу

1. Исходники с понятной структурой папок.
2. `requirements.txt`.
3. SQL-схема или актуальный SQL-дамп — по требованиям задания.
4. ER-диаграмма и блок-схема, если требуются.
5. Инструкция по запуску и краткая памятка по учётным записям.
6. Исполняемый файл — если это явно требуется; он всё равно может нуждаться в доступной базе данных.
7. Финальная проверка запуска из чистого окружения.

## 5. Команды запуска и проверки

```bash
# Активировать окружение перед выполнением
python -m pip install -r requirements.txt
python -m compileall -q .
python main.py
```

Сборка PyInstaller, если нужна:

```bash
# Fedora/Linux
python -m PyInstaller --noconfirm --clean --noconsole --onefile \
  --name ShoeStore --add-data "styles.qss:." main.py
```

В Windows разделитель для `--add-data` обычно `;`, а не `:`.

## 6. Важные ограничения

Этот проект — учебная основа, а не универсальная программа для любого варианта задания. Перед использованием на экзамене сопоставьте каждое требование нового варианта с кодом и схемой. Не запускайте скрипты изменения схемы на единственной копии важной базы без резервной копии. После настройки обязательно протестируйте именно на той базе, с которой будете работать.


## 7. Несовпадения в исходных примерах, которые нужно заметить

В демонстрационном наборе есть товар `Timberland Style Boot`, поэтому в комплектной БД справочник производителей включает `Timberland`. В кратком перечне исходного `manufacturers.csv`, который обсуждался при подготовке, перечислялись только Nike, Adidas, Reebok и Puma. Для ссылочной целостности товара текущий комплект добавляет Timberland. Если на экзамене выдают строго заданные CSV, сверяйте названия с фактическими файлами задания и либо добавляйте отсутствующий справочник, если это разрешено, либо заменяйте демонстрационный товар на согласованный с исходными данными.

Таблица `users` хранит пароль в `password_hash`; CSV-пример `import/users.csv` содержит только логин, ФИО и роль. Пароль в базу импортируется не из открытого CSV: тестовые bcrypt-хеши устанавливает `set_test_passwords.py`.
